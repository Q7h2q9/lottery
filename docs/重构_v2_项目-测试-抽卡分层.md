>
> 起草：2026-05-04

---

## 0. 一句话目标

> 把现有的扁平 `Project = 一个完整任务规格` 模型，拆成
> **项目（容器）→ 测试（配置）→ 抽卡（执行）** 三层；
> 并在"测试"提交跑之前插入一个**撰写 agent**，把用户写的自然语言项目 prompt
> + 用户对每个 agent 的个性化输入综合成 N 条规范的最终 prompt，人审后再跑。

---

## 1. 背景与动机

现状（v1）：
- `Project` 一肩挑：任务描述 + 成功条件 + fleet 规格 + cancel 策略
- 一个 Project 只能跑一种配置；想换 agent 数量、换个性化策略 = 复制粘贴整个 yaml 改
- prompt 必须写 jinja 模板，门槛偏高

用户在 LC48 实战中暴露的需求：
- 一个题目我可能想跑很多种"配置"（10 个全用同一 prompt / 5 个分治 + 5 个穷举 / …）
- 每种配置应该是项目下的"小盒子"，独立保存独立跑历史
- 我希望 prompt 写自然语言，不写 jinja；让一个 LLM 帮我组装成正经 prompt 再跑

## 2. 命名约定

⚠️ 用户原话出现过"测评 agent"指代两个不同角色，本文档统一改用以下命名：

| 本文档命名 | 用户原话 | 角色 |
|---|---|---|
| **撰写 agent** | "提示词生成 agent" / 中间人 / "测评 agent"（之一） | 综合用户输入 → 生成 N 条 prompt 的 LLM |
| **选手 agent** | "做题的 agent" / "测评 agent"（之一） | 实际跑题的 N 个 pi 节点（即原 fleet agent） |
| **格式要求** | "提示词模版格式要求" | 一段自然语言文本，告诉撰写 agent "选手期望啥样的 prompt" |

---

## 3. 数据模型

```
Project（"项目"，可重复利用的容器）
├── id, name
├── base_prompt           ← 自然语言描述（不再要求 jinja）
├── format_spec           ← "格式要求"（位置待定，见 Q1）
├── success_criteria      ← 沿用现有 4 种 + output_regex
└── Test×N（"测试"，挂项目下）
    ├── id, name
    ├── agent_count
    ├── per_agent_overrides:  list[ {hint?, full_prompt_override?} ]
    │                         ← 选项 c：hint 片段 / 完整覆盖 都支持
    │                         ← 数组长度可以 < agent_count，未填的用默认
    ├── resolved_prompts:     list[str]   ← 撰写 agent 产出，N 条具体字符串
    ├── approval_status:      draft | approved
    ├── manual_mode:          bool        ← true 时绕过撰写 agent，直接手写
    └── Draw×N（每次跑一次产生一个 Draw）
        ├── run_id
        ├── status, winner, payload
        └── …（沿用现有 DrawSummary 字段）
```

跟 v1 结构对照：

| v1 | v2 |
|---|---|
| `Project` 含 fleet + 成功条件 + prompt 模板 | `Project` 只剩 base_prompt + format_spec + success_criteria |
| `Draw` 挂 Project | `Draw` 挂 Test |
| 没有 Test | 新增中间层 |
| `prompt` 是 jinja 模板 | `base_prompt` 是自然语言；最终 prompt 由撰写 agent 产出 |
| `FleetEntry.variables` / `FleetEntry.prompt` 给 jinja 用 | 改成 `per_agent_overrides`，是给撰写 agent 的输入 |

---

## 4. 流程

```
① 新建项目  →  写 base_prompt（自然语言）+ format_spec + success_criteria
                            ↓
② 项目下新建 Test  →  设 agent_count，可选填 per-agent 个性化
                            ↓
③ 点"生成 prompt"   →  撰写 agent（zimo gpt-5.4）跑一发，输出 N 条
                            ↓
④ UI 显示 N 张卡片  →  人审，可逐条编辑，可"重新生成"
                            ↓
⑤ 点"批准"          →  resolved_prompts 落库，approval_status=approved
                            ↓
⑥ 点"开始抽卡"     →  跑 Draw（用 resolved_prompts 直接做 fleet 节点）
                            ↓
                Test 改任何配置 → approval_status 回 draft，要重审
```

绕过路径：UI 提供 `manual_mode` 开关，跳过 ③④，用户直接编辑 N 条 prompt 后批准。

## 5. 已决定的事项

来自第 1 轮用户答复（2026-05-04）：

- ✅ **测评 agent 在用户语境里指 fleet agent**（"做题的 agent"），但本文档用"选手 agent"避免歧义
- ✅ **项目 prompt 退化成自然语言**，不再要求 jinja；最终规范由撰写 agent 出
- ✅ **per-agent 个性化用选项 c**：hint 片段 + 完整覆盖都支持，用户填啥撰写 agent 就看啥
- ✅ **撰写 agent 用 zimo gpt-5.4**（即现有 pi 后端 + .env 里的 ZIMO_API_KEY），后续可换
- ✅ **保留手动模式**：用户可绕过撰写 agent 直接写 N 条 prompt，但 UI 默认走撰写流程
- ✅ **Draw 挂 Test 下**：同一 Test 可多次跑，每次产生一个 Draw；Test 内多个 agent 可以共用同一份 prompt

## 6. 已敲定的设计抉择（Q1–Q4）

| Q | 决定 | 含义 |
|---|---|---|
| **Q1 格式要求位置** | (b) **内置默认 + 项目可覆盖** | multidraw 自带一份"prompt 要含任务描述、输出约束、可选 hint…"模板；项目页有"覆盖格式要求"输入框，留空就用默认。约 80% 的项目预期不动。 |
| **Q2 撰写 agent 输出形态** | (a) **N 条具体字符串** | resolved_prompts 是 list[str]，撰写 agent 直接产出每个 agent 的完整 prompt。compiler 不再走 jinja 渲染，直接把字符串塞进 NodeSpec.prompt。 |
| **Q3 撰写触发时机** | (a) **显式按钮** | Test 详情页加"生成 prompt"按钮，用户点了才调撰写 agent。改配置不会自动触发。 |
| **Q4 配置变更后的批准状态** | (c) **用户手动决定** | UI 显示"配置已变更，已批准的 prompts 可能过时"提示，但**不**自动作废；用户自己决定要不要重新生成 + 重审。`approval_status` 仍记录"上次批准时的配置 hash"用于检测漂移。 |

## 7. 新需求：抽卡执行的实时观察（来自第 2 轮）

### 用户原话
> "test 里 agent 输出的时候，最好还是能把所有的就是执行过程还有结果，最好能实时输出到，就是后端前端。
> 就是跑任务的那些 agent 我都要能看到他们的执行过程，就像对话一下吧，agentflow 不是生成了那些 json 吗，感觉能用起来"

### 现状盘点
- **agentflow 已经持久化了所有事件**：`.agentflow/runs/<run_id>/artifacts/<node>/stdout.log`，每条 pi 事件一行 JSON，**22 种事件类型**（HANDOVER #8 验证过）
- **agentflow 自身的 SSE feed 只发节点级事件**：`node_started` / `node_completed` 等，**不**转发选手 agent 内部的 pi 事件流
- **multidraw 现 UI**：抽卡页面是卡片网格，每张卡片只显示状态 chip（pending/running/won/cancelled），**点开看不到对话**
- **关键 pi 事件类型**（`docs/zh_使用手册.md` / HANDOVER 提到）：
  - `thinking`（推理草稿）
  - `message_start` / `message_delta` / `message_end`（assistant 文本）
  - `tool_use` / `tool_result`（工具调用 + 返回）
  - `agent_end`（生命周期完成标记）

### 设计草案

**数据流**：
```
pi 进程     →  写入 stdout.log（agentflow 已做）
              ↓
multidraw    tail -f + 解析 pi 事件（新增 watcher）
              ↓
agentflow SSE feed  ⇄  multidraw SSE 代理（现有 /api/draws/<id>/stream）
              ↓                 ↓
       现有 node_*           新增 agent_event（每条 pi 事件转发）
              ↓                 ↓
              └─→  前端订阅  ←─┘
                       ↓
              卡片可点开，弹出"对话面板"
              展示：thinking 折叠 + 消息流 + 工具调用
```

**前端形态**（草案）：
- 卡片网格仍然是首页，每张卡显示 agent 状态 + 最近一条消息预览（截断 80 字）
- 点击卡片 → 右侧抽屉 / 下方面板展开"对话视图"
  - 时间轴样式：assistant 消息气泡 + 工具调用块（含输入参数 + 返回值预览）
  - thinking 默认折叠，点开看推理
  - 实时滚动；tail mode 默认开
  - Draw 完成后打开仍能看完整对话（从 stdout.log 重放）

**实现位置**：
- 新模块 `multidraw/agent_stream.py`：tail stdout.log + 解析 pi 事件 + 推送
- `racer.py` 的 SSE 订阅扩展，把 agent 事件 multiplex 进 draw 的 SSE feed
- `web/draw.html` + 新 JS 模块写"对话面板"组件
- 不动 agentflow，**纯 multidraw 侧实现**（符合"薄层"原则）

## 8. 已敲定的设计抉择（Q5–Q8）

| Q | 决定 | 含义 |
|---|---|---|
| **Q5 流细节级别** | (c) **项目级 `verbose_stream` 开关，默认精选** | 默认转发：assistant 消息（`message_*`）+ 工具调用（`tool_use` / `tool_result`）+ 生命周期（`agent_end`）。打开 verbose 后才发 `thinking` 等内部事件。开关存在 Project 字段上（`verbose_stream: bool = False`）。 |
| **Q6 重放历史** | (a) **从头重放** | SSE 订阅建立时，服务端先把 stdout.log 已有内容按事件解析一次性吐给客户端（标记为 `replay=True`），再切到实时 tail。前端拿到 replay 事件可批量渲染、不动画。 |
| **Q7 抽卡完成后回看** | (a) **能** | Draw 状态变 `completed/cancelled` 后，agent_stream watcher 停掉但 stdout.log 留着；前端再次打开抽卡页 → 卡片仍可点开 → 服务端纯重放（无 tail）。归档 Draw 也能复盘。 |
| **Q8 多 agent 并发性能** | **按需订阅** | 卡片网格首页只**轻量轮询**（或低频 SSE）拿每个 agent 的状态 + 最近一条消息预览（截断 80 字）；点开某张卡才对那个 agent 发起完整 SSE 订阅；关闭面板时取消订阅。50 agent 不会同时撑 50 路 SSE。 |

### 实现细节（按 Q8 拆出两条端点）

```
GET /api/draws/<did>/stream                 ← 现有 SSE，扩展加 agent_summary（每 N 秒发各 agent 最新预览 + 状态）
GET /api/draws/<did>/agents/<aid>/stream    ← 新增 SSE，单个 agent 的完整事件流（先 replay 再 tail）
```

前端：
- 卡片订阅顶层 stream 拿 summary，渲染卡片预览
- 点开某个 agent → 打开抽屉/面板 → 该面板单独订阅 agent 级 stream
- 关闭面板 → 关掉那条 SSE 连接

## 8. 不变量（重构后仍保持）

来自 CLAUDE.md / HANDOVER.md，重构不能破坏：

1. **race semantics 仍在 agentflow 之外**（外层 racer 不动）
2. **每个 agent 仍是独立 NodeSpec，不用 fanout**（compiler 输出形状不变）
3. **win 条件仍 = agentflow 原生 `node.success`**
4. **`FleetEntry.agent="pi"` 锁定继续保留**（放开是另一个独立 todo）
5. **环境隔离**：撰写 agent 调用 pi 仍走现有 `.env` + `~/.npm-global/bin/pi`，不污染 shell
